# Дополнение к ТЗ v5.1 — Локальные участники и привязка пользователей

> Источник: продуктовое дополнение к Splitser / QHub Split v5.
> Бренд в продукте: **QHub Split** (см. решения v5.0 §0).

## Цель

Упростить начало работы со Splitser, исключив обязательное приглашение пользователей перед созданием комнаты и добавлением расходов.

Пользователь должен иметь возможность вести учёт расходов самостоятельно, добавляя участников как обычные локальные записи, а затем при необходимости приглашать их в комнату без потери истории.

---

## Концепция

Не разделять сценарии «локального учёта» и «совместного использования».

Комната всегда работает одинаково.

Разница лишь в том, привязан ли участник к аккаунту Splitser.

---

## Модель данных

Необходимо разделить понятия:

- Пользователь (User)
- Участник комнаты (Participant)

Участник является самостоятельной сущностью.

Пользователь может быть привязан к участнику, но не является обязательным.

Пример модели:

```text
Participant
------------
id
roomId
name
avatar
linkedUserId?    // null = локальный участник
status
createdAt
```

---

## Статусы участника

Каждый участник может находиться в одном из следующих состояний:

### Local

Локальный участник.

Не имеет аккаунта Splitser.

Существует только внутри комнаты.

Используется для:

- семьи;
- детей;
- друзей;
- организаций;
- любых участников, которых пользователь не хочет приглашать.

---

### PendingInvite

Приглашение отправлено.

Участник ещё не принял приглашение.

После принятия автоматически переходит в состояние Connected.

---

### Connected

Участник привязан к зарегистрированному пользователю Splitser.

Все операции продолжают использовать того же Participant.

Меняется только связь с User.

История операций не изменяется.

---

## Создание участника

Кнопка:

```
Добавить участника
```

После нажатия открывается форма:

- Имя
- Аватар (необязательно)

После сохранения создаётся локальный участник.

Приглашение не требуется.

---

## Приглашение участника

Для любого локального участника доступно действие:

```
Пригласить в Splitser
```

Способы приглашения:

- ссылка;
- QR-код;
- контакт (в будущем).

После принятия приглашения:

- создаётся связь Participant ↔ User;
- все расходы и история сохраняются;
- идентификатор Participant не изменяется.

---

## Работа с расходами

Расходы всегда создаются относительно Participant.

Наличие или отсутствие аккаунта пользователя не влияет на:

- расчёт баланса;
- распределение расходов;
- взаиморасчёты;
- историю операций.

---

## Интерфейс участников

В списке участников отображается статус.

Примеры:

```
Борис
✓ Пользователь Splitser

Алина
Локальный участник

Иван
Приглашение отправлено
```

Статус должен отображаться ненавязчиво.

---

## Сценарий использования

1. Пользователь создаёт комнату.
2. Добавляет локальных участников.
3. Начинает вести учёт расходов.
4. В любой момент может пригласить любого участника.
5. После принятия приглашения участник становится полноценным пользователем Splitser без переноса данных и изменения истории.

---

## Архитектурные требования

1. Все операции должны ссылаться только на Participant.
2. User не должен использоваться в качестве участника расчётов.
3. Participant должен существовать независимо от User.
4. Привязка User является дополнительной возможностью, а не обязательным условием существования Participant.
5. Замена локального участника на подключённого пользователя не должна изменять историю комнаты или требовать миграции данных.

---

## UX-принципы

- Пользователь должен иметь возможность начать пользоваться Splitser без регистрации остальных участников.
- Приглашение является необязательным действием.
- Совместная работа подключается тогда, когда она действительно необходима.
- Интерфейс локального и совместного режима должен быть одинаковым.
- Переход от локального учёта к совместному использованию должен происходить без потери данных и без изменения пользовательского сценария.

---

## Ожидаемый результат

Splitser поддерживает два одинаково важных сценария:

1. **Личный учёт** — пользователь ведёт расходы самостоятельно, используя локальных участников.
2. **Совместный учёт** — локальные участники могут быть в любой момент привязаны к аккаунтам Splitser и начать совместную работу.

Данная архитектура снижает порог входа, сохраняет единый UX и обеспечивает масштабируемость модели без изменения структуры данных.

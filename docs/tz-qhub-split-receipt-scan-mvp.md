# QHub · Общий счёт — ТЗ на MVP «Добавить по чеку»

## Изменения

| Версия | Дата | Суть |
|--------|------|------|
| 0.1 MVP | 2026-07-16 | Первичная спецификация: QR фiscal + OCR фото |
| 0.2 MVP | 2026-07-16 | **KZ:** кассовые чеки без QR; QR на чеках — банковские, **не учитываем**. MVP = только **фото + OCR** |
| 0.2.1 | 2026-07-16 | В UI **не упоминаем QR** — только подсказка про фото чека с ИТОГО |

------------------------------------------------------------------------

# 1. Назначение

Ускорить ввод расхода в сервисе **«Общий счёт»** (`/tools/split`): пользователь фотографирует **кассовый чек**, сервис распознаёт **сумму** и черновик **описания**, пользователь проверяет и сохраняет расход в комнату события (поездка, отдых, компания, семья).

Сервис **не является платёжной системой** — чек нужен только для учёта, не для списания денег.

------------------------------------------------------------------------

# 2. Контекст Казахстана (важно)

## 2.1 Как устроены чеки в РК

| Тип | Как выглядит | Учитываем в «Общий счёт»? |
|-----|--------------|---------------------------|
| **Кассовый (фiscal) чек** | Бумажный термочек: магазин, позиции, **ИТОГО**, БИН, РНМ, ФП — **обычно без QR** | **Да** — через **фото + OCR** |
| **QR на чеке / рядом с оплатой** | Kaspi, Halyk, другие **банковские** QR для перевода или оплаты | **Нет** — это не чек покупки |
| **Электронный чек** | SMS, e-mail, приложение банка / ОФД | **Не в MVP** (нет единого формата импорта) |

**Вывод для продукта:** в Казахстане нельзя опираться на сканирование QR как на основной сценарий. QR на чеке чаще относится к **оплате**, а не к фiscal данным покупки — его **нельзя** использовать для автозаполнения суммы расхода.

## 2.2 Банковские QR (вне MVP)

QR на чеках или слипах оплаты в РК — **банковские**, не кассовые. В MVP **нет** сканера QR в потоке «По чеку»; пользователю **не показываем** подсказки про QR — только съёмку бумажного чека.

*(Внутренняя логика на будущее: если QR всё же попадёт в общий сканер — не использовать для суммы расхода.)*

В MVP **нет отдельного пункта «QR на чеке»** в UI — только **«Сфотографировать чек»**.

------------------------------------------------------------------------

# 3. Связь с продуктом

- **Комната** = событие (поездка, отдых, совместные траты).
- **Расход** = трата участника; после OCR открывается экран **«Проверьте данные»**, затем сохранение.
- **MVP не меняет** логику деления, балансов, погашений, отчётов — только способ **первичного ввода** суммы и описания.

------------------------------------------------------------------------

# 4. MVP — границы

## 4.1 Входит

| # | Функция |
|---|---------|
| 1 | Кнопка **«По чеку»** (или **«Сфотографировать чек»**) в блоке «Добавить расход» |
| 2 | Камера или выбор **фото из галереи** |
| 3 | OCR **на устройстве** (ru / kk / en), как в Сканере документов |
| 4 | Эвристика по строкам **ИТОГО / TOTAL / БАРЛЫҒЫ / К оплате** на кассовом чеке |
| 5 | Экран **«Проверьте данные»** — редактирование перед сохранением |
| 6 | Сохранение обычного `SplitExpense` через существующий API |
| 7 | Опционально: автообрезка/выравнивание кадра (из document-scanner) |

## 4.2 Не входит (явно отложено)

- Сканирование **QR** (фiscal и **особенно банковских**) для суммы расхода.
- Запросы к **OFD / consumer.oofd.kz** и банковским API.
- Импорт **электронных чеков** из SMS / Kaspi / почты.
- Распределение **по позициям чека** (Receipt Items — ТЗ v3.3 §5.7).
- Хранение **фото чека** на сервере.
- AI-категоризация, геолокация, автоматический выбор участников.
- Офлайн-очередь при сохранении — стандартное поведение Split.

## 4.3 За пределами KZ (фаза 2+, не MVP)

В других юрисдикциях на кассовом чеке может быть **фiscal QR** (формат `t=…&s=…&fn=…`). Для qhub.kz в MVP **не реализуем**; при расширении — отдельный флаг региона и фильтр «не банковский QR».

# 5. Пользовательский сценарий (KZ)

**Предусловия:** комната открыта, есть бумажный кассовый чек.

1. Пользователь нажимает **«По чеку»**.
2. Открывается камера (или галерея) — снимок чека целиком, **итоговая часть в кадре**.
3. OCR на устройстве → поиск итоговой суммы.
4. Экран **«Проверьте данные»** с бейджем **«Распознано с фото»**.
5. Пользователь правит сумму/описание при необходимости → **«Сохранить расход»**.
6. Расход создаётся с текущими настройками формы (плательщик, участники, деление).

**Подсказка в UI:** *«Сфотографируйте нижнюю часть чека, где указано ИТОГО.»*

**Отмена:** на любом шаге до сохранения — возврат к форме без изменений.

------------------------------------------------------------------------

# 6. Экраны и UI

## 6.1 Форма «Добавить расход»

Рядом с полем «Сумма» или под заголовком блока:

```
[ 📷 По чеку ]
```

- Только при `room.status === "open"`.
- Не заменяет ручной ввод.

## 6.2 Съёмка / выбор фото

- Одна фотография за попытку.
- Подсказка: держать чек ровно, без бликов; **ИТОГО** в нижней трети кадра.
- Кнопки: **Сделать фото** · **Из галереи** · **Отмена**.

## 6.3 Экран «Проверьте данные»

| Поле | Источник | Редактируемое |
|------|----------|---------------|
| Сумма | OCR | Да, обязательно |
| Валюта | валюта комнаты; в OCR «₸» / «тг» / «KZT» → KZT | Да |
| Описание | первая строка OCR (магазин) или «Чек от ДД.ММ» | Да |
| Категория | эвристика по тексту (§7.4) | Да |
| Источник | бейдж «С фото чека» | Нет |

Кнопки: **Сохранить расход** · **Переснять** · **Отмена**

| Confidence | UI |
|------------|-----|
| `medium` | OCR нашёл «ИТОГО» в той же строке с суммой |
| `low` | сумма по эвристике «max внизу» — жёлтая плашка *«Проверьте сумму вручную»* |

# 7. OCR кассового чека (KZ)

## 7.1 Пайплайн

1. (Опционально) автообрезка / perspective fix — из Сканера документов.
2. OCR: **ru**, **kk**, **en**.
3. Нормализация: пробелы в числах (`1 234,00` → `1234.00`).

## 7.2 Эвристика суммы (приоритет)

Искать строки (регистронезависимо):

1. `ИТОГО`, `ИТОГ`, `TOTAL`, `К ОПЛАТЕ`, `СУММА`, `БАРЛЫҒЫ`, `ТӨЛЕМ`
2. Рядом — число `\d+[.,]\d{2}` (допускать пробелы как разделитель тысяч).
3. Несколько кандидатов → **максимальное** из **нижней половины** текста.
4. **Исключить:** строки с `НДС`, `VAT`, `СДАЧА`, `БОНУС`, `КЕШБЭК`, `КЕШБЕК`, `НАЛИЧНЫ`, `БЕЗНАЛ` если сумма меньше явного итога.
5. **Исключить:** суммы из блока «оплата картой / kaspi / перевод» если ниже уже есть **ИТОГО** (типичный банковский слип рядом с чеком на одном фото — брать ИТОГО чека, не сумму перевода).

## 7.3 Черновик описания

- Первая осмысленная строка (не дата, не БИН/ИИН, не «ТОО»/«ИП» отдельно) — до 40 символов.
- Fallback: `Чек от 16.07.2026`.

## 7.4 Категория (предложение)

| Ключевые слова в OCR | categoryId |
|----------------------|------------|
| magnum, small, market, продукт, ресторан, кафе, coffee | `food` |
| такси, yandex, uber, бензин, заправка, azs | `transport` |
| hotel, отель, hostel | `stay` |
| иначе | `other` |

## 7.5 Confidence

| Уровень | Условие |
|---------|---------|
| `medium` | ключевое слово итога и сумма **в одной строке** |
| `low` | сумма только по эвристике «max внизу» |

**`high`** в KZ-MVP **не используется** (нет доверенного QR-источника).

------------------------------------------------------------------------

# 8. Банковские QR (только для разработки, не UI)

В пользовательском интерфейсе **не упоминаем** QR и не показываем ошибок про «QR для оплаты».

| Признак | Действие (если когда-нибудь попадёт в общий сканер) |
|---------|-----------------------------------------------------|
| URL банка / платёжки (`kaspi.kz`, `halyk`, …) | не использовать для суммы расхода |
| QR на слипе терминала | не путать с ИТОГО кассового чека на фото |

В KZ-MVP сканер QR в поток «По чеку» **не входит**.

------------------------------------------------------------------------

# 9. Интеграция с QHub

## 9.1 Маршруты MVP

| Путь | Роль |
|------|------|
| `/tools/split/room?room=…` | форма расхода + review после OCR |
| `/tools/document-scanner?mode=receipt&returnTo=…` | **основной** путь: фото → OCR → `scan-return` |

Альтернатива: встроенная камера **внутри** Split без перехода в document-scanner (тот же OCR-модуль).

## 9.2 Контракт `scan-return`

JSON в `sessionStorage`:

```typescript
interface ReceiptScanPayload {
  source: "ocr_receipt";   // единственный источник в KZ-MVP
  amount: string;
  currency?: string;
  description?: string;
  confidence: "medium" | "low";
  ocrExcerpt?: string;     // до 200 символов для UI
}
```

Параметры URL: `room=…`, `receipt=1`, `scanKey=…`

## 9.3 Сохранение расхода

Существующий `POST …/expenses`:

```json
{
  "description": "Magnum · чек 16.07",
  "amountOriginal": "5840.00",
  "currencyOriginal": "KZT",
  "categoryId": "food",
  "comment": "ocr:confidence=medium",
  "clientMutationId": "…"
}
```

**MVP:** новых полей не требуется — `comment` с префиксом `ocr:`.

**Фаза 2:** `ExpenseReceiptMeta`, опциональное фото-вложение.

# 11. Ошибки

| Ситуация | Сообщение |
|----------|-----------|
| OCR не нашёл сумму | «Не нашли ИТОГО на чеке. Переснимите нижнюю часть или введите сумму вручную.» |
| Сумма 0 или > 10 млн | «Проверьте сумму — значение выглядит неправильно.» |
| Комната archived | кнопка скрыта |
| Нет камеры | «Выберите фото из галереи.» |

------------------------------------------------------------------------

# 12. Критерии приёмки MVP (KZ)

1. Фото термочека с «ИТОГО 5 840,00» → на review сумма **5840.00** (или правка пользователем).
2. После сохранения баланс и отчёт как при ручном вводе.
3. Отмена на review не создаёт расход.
4. Работает во всех типах комнат.
5. OCR выполняется **на устройстве**; полный текст чека не уходит на сервер.

------------------------------------------------------------------------

# 13. План реализации

| Этап | Объём |
|------|-------|
| **MVP** | Кнопка «По чеку» → камера/галерея → OCR → review → сохранение |

# 14. Открытые вопросы

1. **Дата траты:** отдельное поле или в описании / `comment`?
2. **Встроенная камера vs document-scanner:** один экран в Split или переход в инструмент?
3. **Два чека на одном фото** (магазин + банковский слип): достаточно ли эвристики «ИТОГО выше суммы перевода»?

**Рекомендации для MVP:**

- встроенная камера в Split с общим OCR-модулем;
- дату — в описание;
- при двух итогах на фото — показывать **оба кандидата** на review, пользователь выбирает.

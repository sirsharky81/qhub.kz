# QHub · Общий счёт — ТЗ на MVP «Добавить по чеку»

## Изменения

| Версия | Дата | Суть |
|--------|------|------|
| 0.1 MVP | 2026-07-16 | Первичная спецификация: QR фискального чека + OCR фото, без позиций и без OFD API |

------------------------------------------------------------------------

# 1. Назначение

Ускорить ввод расхода в сервисе **«Общий счёт»** (`/tools/split`): пользователь сканирует **QR с кассового чека** или делает **фото чека**, сервис подставляет **сумму** и **черновик описания**, пользователь проверяет и сохраняет расход в комнату события (поездка, отдых, компания, семья).

Сервис по-прежнему **не является платёжной системой** — чек нужен только для учёта, не для списания денег.

------------------------------------------------------------------------

# 2. Связь с продуктом

- **Комната** = событие (поездка, отдых, совместные траты).
- **Расход** = трата участника; после сканирования открывается та же форма «Добавить расход», но с предзаполненными полями.
- **MVP не меняет** логику деления, балансов, погашений, отчётов — только способ **первичного ввода** суммы и описания.

# 3. MVP — границы

## 3.1 Входит

| # | Функция |
|---|---------|
| 1 | Кнопка **«По чеку»** в блоке «Добавить расход» (комната в статусе `open`) |
| 2 | Выбор способа: **QR на чеке** или **Фото чека** |
| 3 | **QR (фiscal):** распознавание payload, извлечение суммы, даты, ссылки на проверку |
| 4 | **Фото:** OCR на устройстве, эвристика по строке «ИТОGO» / «TOTAL» / «К оплате» |
| 5 | Экран **«Проверьте данные»** — редактирование перед сохранением |
| 6 | Сохранение обычного `SplitExpense` через существующий API |
| 7 | Переиспользование **Сканера кодов** (QR) и OCR-пайплайна **Сканера документов** |
| 8 | Возврат в комнату через механизм `scan-return` (`scanKey` + `sessionStorage`) |

## 3.2 Не входит (явно отложено)

- Распределение **по позициям чека** (Receipt Items — см. ТЗ v3.3 §5.7).
- Запросы к **OFD / consumer.oofd.kz / proverkacheka** за полным JSON чека (магазин, позиции, НДС).
- Хранение **фото чека** на сервере (вложения к расходу).
- AI-категоризация, геолокация по чеку, автоматический выбор участников.
- Сканирование **штрихкода товара** (EAN) — только фiscal QR или фото итога.
- Офлайн-очередь: если нет сети при сохранении — стандартное поведение Split (ошибка API).

# 4. Пользовательские сценарии

## 4.1 QR на чеке (основной, KZ)

**Предусловия:** комната открыта, у пользователя есть фiscal QR на бумажном или электронном чеке.

1. Пользователь нажимает **«По чеку»** → **«QR на чеке»**.
2. Открывается **Сканер кодов** с `returnTo=/tools/split/room?room=…&receipt=1`.
3. После успешного скана — возврат в комнату с `scanKey`.
4. Клиент парсит payload → экран **«Проверьте данные»**.
5. Пользователь правит при необходимости → **«Сохранить расход»**.
6. Расход создаётся с текущими настройками формы (плательщик, участники, способ деления, личный/общий).

**Ожидаемое время:** 5–15 секунд при нормальном QR.

## 4.2 Фото чека (fallback)

**Предусловия:** QR повреждён, отсутствует или не фiscal.

1. **«По чеку»** → **«Фото чека»**.
2. Камера или выбор из галереи (один кадр).
3. OCR (локально, как в Сканере документов: ru / kk / en).
4. Эвристика ищет итоговую сумму → экран **«Проверьте данные»** с пометкой **«Распознано с фото — проверьте сумму»**.
5. Сохранение как в 4.1.

## 4.3 Отмена

На любом шаге до сохранения — **«Отмена»** → возврат к форме расхода без изменений.

# 5. Экраны и UI

## 5.1 Форма «Добавить расход» (изменение)

Под полем «Сумма» или рядом с заголовком блока:

```
[ По чеку ]
```

- Видна только при `room.status === "open"`.
- Не блокирует ручной ввод — чек **дополняет**, не заменяет форму.

## 5.2 Bottom sheet «Как добавить по чеку?»

| Вариант | Подпись |
|---------|---------|
| QR на чеке | Быстро и точно, если на чеке есть QR |
| Фото чека | Если QR нет или не читается |

## 5.3 Экран «Проверьте данные»

| Поле | Источник | Редактируемое |
|------|----------|---------------|
| Сумма | QR `s` / OCR | Да, обязательно |
| Валюта | валюта комнаты по умолчанию; если в OCR «₸»/«тг» → KZT | Да |
| Описание | черновик: «Чек от ДД.ММ» или название из OCR | Да |
| Категория | эвристика (см. §7.3) | Да |
| Дата траты | QR `t` / сегодня | Да (если поле даты добавят в форму; иначе — в `comment`) |
| Источник | бейдж: «QR чека» / «Фото (проверьте)» | Нет |

Кнопки: **Сохранить расход** · **Назад к форме** · **Сканировать снова**

При `confidence: low` (OCR) — жёлтая плашка: «Сумма распознана неточно — проверьте вручную».

# 6. Форматы QR (Казахстан и совместимость)

## 6.1 Типичный payload (query string)

На многих чеках РК и РФ QR кодирует **строку параметров** (иногда внутри URL):

```
t=20250716T1430&s=5840.00&fn=9282440300829880&i=10556&fp=189504453&n=1
```

| Параметр | Значение | Использование в MVP |
|----------|----------|---------------------|
| `t` | дата/время `YYYYMMDDThhmm` или `…ss` | дата траты, описание |
| `s` | сумма покупки (десятичная) | **amountOriginal** |
| `fn` | заводской/фiscal номер ККМ | метаданные в `comment` |
| `i` | номер фiscal документа | метаданные |
| `fp` / `fpd` | фiscal признак | метаданные |
| `n` | тип операции (1 = приход) | валидация (опционально) |

## 6.2 URL-обёртка

QR может быть полным URL, например:

- `https://consumer.oofd.kz?…`
- другие домены ОФД (Jusan, Kazakhtelecom и т.д.)

**Правило парсинга MVP:** извлечь `search` / query из URL; если не URL — трактовать всю строку как query string.

## 6.3 Валидация MVP

| Проверка | Действие |
|----------|----------|
| Есть `s` и парсится как число > 0 | OK |
| Нет `s` | ошибка «Не удалось прочитать сумму из QR» |
| `n` ≠ 1 (возврат) | предупреждение «Это чек возврата — проверьте сумму» |
| Дубль QR в той же комнате за последние N минут (fn+i+fp) | мягкое предупреждение, не блокировать |

## 6.4 Без OFD API в MVP

**Не вызываем** `consumer.oofd.kz` и сторонние API для получения JSON чека.

Достаточно **локального парсинга** QR — сумма и дата уже в payload.

**Фаза 2 (не MVP):** опциональный запрос к OFD для названия магазина и позиций.

# 7. OCR фото чека

## 7.1 Пайплайн

1. Обрезка/выравнивание (опционально, из Сканера документов).
2. OCR: языки **ru**, **kk**, **en** (как в document-scanner).
3. Нормализация текста: пробелы, запятая/точка в суммах.

## 7.2 Эвристика суммы (приоритет)

Искать строки (регистронезависимо):

1. `ИТОГО`, `ИТОГ`, `TOTAL`, `К ОПЛАТЕ`, `СУММА`, `БАРЛЫҒЫ`
2. Рядом с ключевым словом — число формата `\d+[.,]\d{2}`
3. Если несколько кандидатов — взять **максимальное** из нижней половины текста (итог обычно внизу).
4. Исключить строки с `НДС`, `VAT`, `СДАЧА`, `БОНУС` если сумма явно меньше итога.

## 7.3 Черновик описания

- OCR: первая осмысленная строка (не дата, не ИИН/БИН) → до 40 символов.
- Fallback: `Чек от 16.07.2026`.

## 7.4 Категория (предложение, не блокирующее)

| Ключевые слова в OCR | categoryId |
|----------------------|------------|
| ресторан, кафе, coffee, magnum, small, market, продукт | `food` |
| такси, yandex, uber, бензин, заправка, azs | `transport` |
| hotel, отель, hostel | `stay` |
| иначе | `other` |

## 7.5 Confidence

| Уровень | Условие |
|---------|---------|
| `high` | QR с `s` |
| `medium` | OCR + ключевое слово «ИТОГО» в той же строке |
| `low` | OCR, сумма найдена только по эвристике «max внизу» |

# 8. Интеграция с QHub (архитектура)

## 8.1 Контракт `scan-return` (расширение)

Существующий механизм (`storeScanResult` / `consumeScanResult`) хранит **строку**.

**MVP:** хранить JSON-строку:

```typescript
interface ReceiptScanPayload {
  source: "fiscal_qr" | "ocr_receipt";
  amount: string;           // "5840.00"
  currency?: string;        // "KZT"
  description?: string;
  purchaseDate?: string;    // ISO 8601
  confidence: "high" | "medium" | "low";
  fiscal?: {
    fn?: string;
    i?: string;
    fp?: string;
    n?: string;
    verifyUrl?: string;     // если QR был URL
  };
  ocrExcerpt?: string;      // первые 200 символов для отладки UI
}
```

Параметры URL при возврате:

- `room=<roomId>` — как сейчас
- `receipt=1` — флаг «открыть экран проверки чека»
- `scanKey=<uuid>` — как в мессенджере

## 8.2 Маршруты

| Путь | Роль |
|------|------|
| `/tools/split/room?room=…` | потребляет `scanKey`, показывает review |
| `/tools/code-scanner?…&returnTo=…` | QR |
| `/tools/document-scanner?…&returnTo=…&mode=receipt` | фото + OCR (новый mode) |

## 8.3 Парсинг QR — где выполнять

**Клиент** (`SplitRoomClient` или `lib/split/receipt/parse-fiscal-qr.ts`):

- без серверного round-trip для MVP;
- проще для приватности (фiscal данные не уходят на сервер до сохранения расхода).

## 8.4 Сохранение расхода

Без нового API: существующий `POST …/expenses` с телом:

```json
{
  "description": "Magnum · чек 16.07",
  "amountOriginal": "5840.00",
  "currencyOriginal": "KZT",
  "categoryId": "food",
  "paidByMemberId": "…",
  "splitMethod": "equal",
  "participants": [ … ],
  "comment": "fiscal:fn=…;i=…;fp=…;src=qr",
  "clientMutationId": "…"
}
```

Поле `comment` — для трассировки источника, пока нет `receiptMeta` в модели.

# 10. Ошибки и краевые случаи

| Ситуация | Сообщение пользователю |
|----------|------------------------|
| QR не фiscal / нет `s` | «Не удалось прочитать сумму. Попробуйте фото чека.» |
| OCR не нашёл сумму | «Не нашли итог на чеке. Введите сумму вручную.» |
| Сумма 0 или > 10 млн | «Проверьте сумму — значение выглядит неправильно.» |
| Комната archived | кнопка «По чеку» скрыта |
| Нет доступа к камере | «Разрешите камеру или выберите фото из галереи.» |
| Дубликат clientMutationId | стандартная идempotency Split |

------------------------------------------------------------------------

# 11. Приватность и безопасность

- OCR и парсинг QR — **на устройстве** (как Сканер документов).
- На сервер уходит только то, что пользователь **сохранил** как расход (+ опциональный `comment` с fn/i/fp).
- Фото чека в MVP **не загружается** на сервер.
- Не логировать полный OCR-текст на backend.

------------------------------------------------------------------------

# 12. Критерии приёмки MVP

1. Фiscal QR с `s=1234.56` → на экране проверки сумма **1234.56**, сохранение создаёт расход с этой суммой.
2. Фото термочека с строкой «ИТОГО 1 234,00» → сумма распознана или пользователь правит на review.
3. После сохранения баланс и отчёт пересчитываются как при ручном вводе.
4. Отмена на review не создаёт расход.
5. Работает в комнатах всех типов (`individual`, `own_family`, `multi_family`).
6. Возврат из Сканера кодов не теряет контекст комнаты (`roomId`).

# 14. Открытые вопросы

1. **Дата расхода:** сейчас `SplitExpense` не имеет отдельного `expenseDate` — использовать `createdAt` или добавить поле?
2. **Валюта чека ≠ валюта комнаты:** конвертировать по курсу комнаты автоматически или предупреждать?
3. **Единый entry point:** одна кнопка «По чеку» или отдельно «QR» и «Фото» в форме?
4. **Дубликаты:** блокировать повторное сканирование того же fn+i+fp или только предупреждать?

**Рекомендации для MVP:**

- дату класть в `comment` или описание, отдельное поле — в 2.0;
- валюта чека = валюта комнаты, иначе ручная правка на review;
- одна кнопка «По чеку» → bottom sheet;
- дубликаты — только предупреждение.
